# Как устроен репозиторий и как его развивать

## Первый ориентир
Начните с [START_HERE.md](START_HERE.md). В корне намеренно оставлены `README.md` (знакомство), `PROJECT_STATE.md` (текущее состояние), `TASKS.md` (дорожная карта), `CHANGELOG.md` (история), `DECISIONS.md` (принятые решения).

**Существующие директории:** `nirs_satellite/` — код; `scenarios/` — входы; `tests/` — проверки; `docs/` — методика; `results/` — результаты запуска. Сейчас папку кода НЕ переносим ради косметики.

## Целевая структура (постепенно)
```text
nirs-satellite/
├── README.md
├── pyproject.toml             # зависимости, entry points — после перехода на пакет
├── src/nirs_satellite/
│   ├── mission/              # задания и требования
│   ├── physics/              # адаптер геометрии и ресурсов, внешние библиотеки
│   ├── scheduling/           # baseline и разрабатываемый метод
│   ├── simulation/           # исполнитель расписаний
│   └── evaluation/           # KPI
├── scenarios/
│   ├── synthetic/            # контрольные искусственные задачи
│   └── study/                # исследовательские входные данные с происхождением
├── tests/                    # модульные и интеграционные проверки
├── benchmarks/               # небольшие фиксированные эталоны с ответами
├── experiments/              # сценарии воспроизводимых запусков
├── results/                  # генерируемые результаты, обычно не в Git
├── docs/                     # модель, источники, ограничения, протоколы
└── .github/workflows/        # автоматические проверки
```

Не заводить пустые модули «на будущее»: структура расширяется вместе с работающим кодом. Массовый перенос проводить отдельным PR после фиксации тестов.

## Git-процесс
1. Основная ветка `main` всегда должна запускаться и проходить тесты.
2. На одну осмысленную задачу — отдельная ветка, например `feature/scheduling-v02`.
3. Делать коммит с описанием изменения и ссылки на задачу, а не «update».
4. Открывать Pull Request: что изменилось, откуда параметры, что проверено, что не проверено.
5. Сливать в `main` только после проверки, версию/результаты фиксировать в `PROJECT_STATE.md`, `CHANGELOG.md`.
6. Для результатов вычислений сохранять входной JSON, commit SHA, версию Python/библиотек, дату, исходные данные, seed и логи.

## Как хранить результаты
- В Git: исходные конфигурации, эталонные небольшие входы/выходы, тесты, воспроизводящие инструкции, краткие таблицы итогов.
- Не в Git по умолчанию: большие промежуточные файлы, временные картинки, скачанные архивы погоды, виртуальные окружения и кеши.
- Синтетические, паспортные и измеренные значения никогда не смешивать без признака происхождения.

## Минимальные условия приёмки изменений
- Тесты пройдены; при изменении математического правила добавлен контрольный пример.
- Документированы единицы, допущения и статус достоверности.
- Файлы нового модуля доступны через `README.md` или `docs/START_HERE.md`.
- Нет скрытого копирования кода с непроверенной лицензией.

## Важное ограничение
На момент написания это **проект предлагаемой организации**, а не уже перенесённые папки. Эту ветку можно изучать и обсуждать до слияния в `main`.
