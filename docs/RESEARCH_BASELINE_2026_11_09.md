# Исследовательская база Mission 02 (09.11.2026)

## Статус и граница применения

Основа разработки — `feature/mission-01-datachain`, коммит
`2591766866b32e16ce731b87baf504df6ec12e2f`.
Исходная реализация **не переписана**. Добавлен сценарий
`experiments/mission_02/` и отдельный workflow `mission02.yml`.

**Терминология**:
- «Физическая орбита» — численно проинтегрирована модулями Basilisk на
  *заданных синтетических* начальных условиях;
- «Операционные ограничения» — собственные приближения по геометрии,
  времени манёвров, энергии, памяти, скорости передачи и срокам;
- «Доставлено» — полностью списано из моделируемого буфера за время
  геометрического окна, а не фактически принято земной аппаратурой.

## Состав и происхождение

| Подсистема | Исполнитель | Степень проверки |
|---|---|---|
| Движение по орбите | Basilisk spacecraft + point-mass Earth gravity | Ground 01, орбитальная аналитика и CI |
| Вращение Земли, геометрия | Basilisk planetEphemeris + groundLocation в Ground 01, собственная сферическая геометрия в Mission 02 | Верификация Ground 01; Mission 02 unit-tests |
| Исполнение одноразовой съёмки и радио | Basilisk simpleInstrumentController, simpleInstrument, storage, transmitter в **Mission 01** | Mission 01 Windows/Linux CI |
| Несколько заданий и политики | Собственная `mission_02/model.py` | Набор unit-tests + Linux/Windows GitHub Actions |
| Наведение Mission 02 | Упрощённая минимальная кинематическая длительность по ограниченному моменту, скорости и моменту RW | **Не** полная модель реакционных колёс |
| Энергетика Mission 02 | Собственные Wh-ограничения и идеализированная тень | **Не** Basilisk simpleBattery, eclipse или solarPanel |
| Радиолиния Mission 02 | Friis/EbN0, номинальный максимум, пакеты, доступность станции | **Не** симуляция BER/кодирования/ACK |
| Журналы, сравнения | Python / JSON / CSV, SHA-256 трека и входов | Машинные проверки |

**Предельная точность результатов соответствует самому слабому из
использованных приближений**, а не наличию физического движка Basilisk
в цепочке подготовки данных.

## Контрольные параметры

- Базовая орбита из `inputs/physical/orbit.json`:
  синтетическая круговая 500 км, i=45°, RAAN=30°, масса 10 кг.
- Исследовательский набор из 8 условных географических задач.
- Две условные наземные станции.
- Память 4 000 000 байт, пакет 5 000 байт.
- Запас батареи 80 Wh, начальный заряд 65 Wh, резерв 5 Wh.
- Условный радиоканал S-диапазона 2,2 ГГц, потолок 160 кбит/с.
- Три независимых политики FIFO, EDF, Priority.
- Пользователь может изменять параметры в JSON или через CLI с
  автоматической записью `configuration_used.json`.
- Временная эпоха произвольная, не привязана к UTC; вектор Солнца условен.

Числа не являются данными изготовителя аппаратуры. Параметры
радиолинии и массы должны быть заменены после выбора паспорта конкретного КА.

## Требования к принятию версии

1. Проверить `python -m unittest discover -s tests -p test_mission02_model.py -v`.
2. Прогнать одну и ту же Mission 02 на Linux и Windows с Basilisk 2.12.2.
3. Проверить точное сохранение бит: generated = transmitted + stored.
4. Убедиться, что начальная память и батарея никогда не выходят за границы.
5. Выполнить серию параметрических запусков с зафиксированным SHA-256 трека.
6. Убедиться, что новые изменения не нарушили baseline Mission 01.
7. Сохранить результаты и ссылки на конкретные CI-коммиты; не подменять
   отсутствие hardware-validation словом «проверено».

## Научная исследовательская задача

Первый формализованный вопрос: как выбор политики планирования наблюдений
и передачи данных изменяет взвешенную долю заданий, условно
доставленных в срок при ограниченных ресурсах одного аппарата?

Первые управляемые параметры: память, скорость канала, запас энергии,
приоритеты и сроки задания. Возможности сравнения должны учитывать
дискретный шаг, чувствительность к сценарию и повторение на разных наборах
синтетических целей. Нельзя судить по одному сценарию.

## Физические доработки по приоритету

1. **RW**: в Mission 01 / расширенном ADCS применить официальные
   `reactionWheelStateEffector`, `rwMotorTorque`, `simIncludeRW`; собрать
   эталон времени перенаведения и насыщения для Mission 02.
2. **Power**: реальная интеграция `simpleSolarPanel`, `eclipse`,
   `simpleBattery` и `simplePowerSink` для получения калибровочных
   энергетических профилей разных режимов.
3. **Multi-target physical replay**: команды Mission 02 должны управлять
   физической ориентацией и многократной съёмкой в Basilisk, а не только
   дискретной реализацией задач. Это обязательно до окончательного
   утверждения результатов НИР.
4. **RF**: калибровка номинальных скоростей по документированному
   радиобюджету и независимая проверка доставки.
5. **Higher-fidelity orbit**: J2, UTC, WGS84 и при необходимости
   атмосферное торможение; независимый эталон.
6. **Оптимизация**: OR-Tools CP-SAT как нижняя/верхняя граница качества
   для небольших задач, с честным статусом solver и шагом сетки.
