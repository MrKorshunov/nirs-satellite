# Универсальная физическая Mission 04: точечные и полосные наблюдения

**Дополнение Mission05:** новая версия исполнителя поддерживает плановые интервалы съёмки и связи, отчёты план/факт, UTC-эпоху и измерение WGS84-площади перекрываемых регионов с объединением повторно покрытых участков. Изложенные ниже ограничения и исходные определения относятся к исходному этапу Mission04; актуальная геометрия и модельные границы — в [SCIENTIFIC_READINESS_MISSION05.md](SCIENTIFIC_READINESS_MISSION05.md).

**Назначение:** исполнитель физических заданий на одном КА без каких-либо алгоритмов оптимизации. Один непрерывный процесс Basilisk 2.12.2, одна орбита, одна динамика корпуса с тремя реакционными маховиками, реальные Basilisk сообщения прибора, памяти, радиопередатчика и энергетики.

## Что теперь умеет исполнитель

- Принимать **1–64 предварительно упорядоченных заданий** из JSON. Верхняя граница защищает память и время расчёта; это не предел космического аппарата.
- **Point:** повернуться к заданным широте/долготе, дождаться геометрического доступа, реального допустимого наведения и энергетического допуска, сформировать один продукт заданного объёма.
- **Strip (первый этап):** переключиться в **надирное наведение**, следить за фактической подспутниковой точкой по положению КА и ориентации Земли, формировать порции данных в последовательных физических тактах, **только когда поперечная полоса пересекает заданную территорию**.
- Для каждой задачи иметь отдельный раздел Basilisk `PartitionedStorageUnit`; физический `spaceToGroundTransmitter` списывает накопленные биты при геометрическом контакте со станцией.
- При недостаточном заряде или заполнении памяти не разрешать новую съёмку. Физические режимы `SimplePowerSink` (камера/радио) переключаются контроллером. Вращение Земли, аккумулятор, маховики и движение КА при смене цели **не перезапускаются**.
- Соблюдать заданный **порядок**, моменты `release_s` и `deadline_s`, регистрировать пропуск и его причину. **Не выбирать оптимальную последовательность.**

## Обычный запуск на Windows

1. Обновить ветку `main` через GitHub Desktop.
2. Запустить `START_NIRS.cmd`.
3. Выбрать **«Физический КА: точечная + полосная съёмка (без оптимизации)»**.
4. Оставить 0,2 часа и включить запись Vizard.
5. Нажать **«Запустить»**, затем открыть результаты.

Условная эталонная программа: **две точечные цели, затем полоса** над `CORRIDOR_ALPHA` с 12 последовательными строками. Все данные условные.

## Где вводить географические территории и аппаратные параметры

В интерфейсе кнопка **«Все исходные данные»** или редактирование JSON в VS Code.

| Файл | Что изменяется |
|---|---|
| `inputs/physical/mission_mixed_demo.json` | Порядок заданий, вид `point`/`strip`, ID, сроки, порции данных, угол полосы |
| `inputs/physical/territories.json` | Территории в виде замкнутого по смыслу многоугольника `[[lat,lon], ...]` на вращающейся сферической Земле |
| `inputs/physical/orbit.json` | Начальная орбита, масса, моменты инерции |
| `inputs/physical/adcs_wheels.json` | Реакционные маховики и регулятор |
| `inputs/physical/power.json` | Панель, аккумулятор, нагрузка |
| `inputs/physical/camera_storage_radio.json` | Ёмкость накопителя, параметры съёмки и передачи |

**Территории действительно связаны с орбитой:** текущая широта/долгота подспутниковой точки вычисляется **из физического состояния `spacecraft.scStateOutMsg` и DCM `planetEphemeris.J20002Pfix`**. При изменении наклонения, высоты или начальной аномалии трасса изменится, и исходная территория может перестать пересекаться со съёмочной полосой. Это корректный физический отказ задания, а не программная ошибка.

`territories.json` задаёт список объектов:
```json
{
  "scenario_id": "regions_example",
  "provenance": "SYNTHETIC geometry",
  "frame": "planet_fixed_spherical_lat_lon_deg",
  "regions": [
    {
      "id": "AREA_01",
      "polygon_lat_lon_deg": [[17.8,47.1],[17.8,54.3],[24.0,54.3],[24.0,47.1]]
    }
  ]
}
```

Это **планетографические широта и долгота в синтетическом, вращающемся глобусе**, а не реальная дата наблюдения: привязки к UTC пока нет.

## Формат задания и контракт с будущим планировщиком

Поле `kind` определяет поведение:

```json
{
  "id": "POINT_01",
  "kind": "point",
  "lat_deg": 14.0,
  "lon_deg": 43.0,
  "altitude_m": 0,
  "minimum_elevation_deg": 10,
  "maximum_range_m": -1,
  "release_s": 0,
  "deadline_s": 720
}
```

```json
{
  "id": "STRIP_01",
  "kind": "strip",
  "region_id": "AREA_01",
  "look_direction": "nadir",
  "fov_cross_track_deg": 15,
  "sample_bytes": 5000,
  "min_samples": 12,
  "max_samples": 12,
  "release_s": 0,
  "deadline_s": 720
}
```

В будущем наш планировщик сможет **создать JSON со строго таким контрактом**, ничего не меняя в физическом двигателе:

```json
{
  "schema_version": 1,
  "scenario_id": "external_fixed_order",
  "provenance": "SYNTHETIC external task selection",
  "execution_policy": "provided_order_only",
  "tasks": [
    {"id":"POINT_01","kind":"point","lat_deg":14.0,"lon_deg":43.0,
     "altitude_m":0,"minimum_elevation_deg":10,"maximum_range_m":-1,
     "release_s":0,"deadline_s":720}
  ]
}
```

Запуск для разработчика (из корня репозитория, в VS Code или терминале):
```text
.venv\Scripts\python.exe -m experiments.mission_03.run --config inputs/physical/mission_execution.json --program external_fixed_order.json --regions inputs/physical/territories.json --duration-hours 0.2 --viz-mode off --require-all-complete --output-name external_run_01
```

`--program` **не выбирает** порядок, не решает задачу оптимизации и не изменяет паспорт аппаратуры. Просто принимает список готовых заданий и исполняет их по очереди. Наличие дедлайнов не означает алгоритма планирования.

## Как вычисляется полоса

На каждом физическом шаге `Δt=0,5 с`:

1. Берём `r_CN_N` из `spacecraft`, применяем матрицу вращения `J20002Pfix`, вычисляем планетографические широту/долготу подспутниковой точки.
2. `groundLocation` переносится в надирную подспутниковую точку; `locationPointing`, `mrpFeedback` и **реакционные маховики Basilisk** физически разворачивают прибор и сопровождают эту точку.
3. По высоте `h` и поперечному углу поля зрения `FOV` оцениваем ширину полосы **на локальной касательной плоскости**:
   `W ≈ 2 h tan(FOV/2)`.
4. Из расстояния подспутниковой точки до многоугольника в локальной проекции определяем геометрическое пересечение полосы с территорией. Если доступ, наведение, память и энергия позволяют, штатный `simpleInstrument` генерирует `sample_bytes` данных.
5. Только **фактически записанное Basilisk сообщение прибора** считается строкой съёмки. После `max_samples` управление передаётся следующему заданию.

### Что эта модель НЕ обещает

Физическое движение КА и наведение рассчитываются Basilisk. Однако **саму оптику камера пока не моделирует**: нет разрешения пикселей, GSD, смаза, реальных кадров, точного отсечения изображения границей многоугольника, качества света, рельефа, облаков. Площадь `approx_swath_sample_area_m2` — приближённая производная от длины последовательных отсчётов и ширины полосы, **не точная площадь территории, действительно покрытая изображением**. При высоких широтах, антимередиане или больших территориях требуется более точная геодезическая модель.

`min_samples` — минимальное число порций для оценки завершённости, `max_samples` — лимит демонстрационного режима; они **не гарантируют** требуемое процентное покрытие всей территории. Позже для научного KPI покрытия потребуется независимый расчёт пересечения реальных footprint-полигонов с областью и процент площади.

## Где посмотреть фактическую траекторию и результаты

Каждый запуск содержит:

- `mission03_groundtrack.csv`: реальная подспутниковая трасса и активное задание (вся орбита).
- `mission03_strip_footprints.csv`: каждая **фактически созданная** строка, широта/долгота, высота, поперечная ширина и расстояние до области.
- `mission03_events.json`: последовательность назначений, завершений, пропусков и энергозапретов.
- `mission03_states.csv`: физическое наведение, состояние буфера, батареи и маховиков.
- `mission03_summary.json`: выполняемые и пропущенные задачи, битовый баланс, проверки и степень выполнения.
- `execution_program_used.json`, `territories_used.json`: точная копия исходного задания и территории для воспроизводимости.
- `mission03_dataflow.png`, `power_summary.json` и файл Vizard (`.bin`).
- В Vizard территория обозначается **центральным маркером и вершинами полигона**, не заполненной текстурой.

Не следует сравнивать расписания по одному примеру. Пока проверяется **физический исполнитель**, а метод поиска оптимального порядка и алгоритмы намеренно отсутствуют.

## Что сохраняется без изменений

Предыдущий двухточечный режим Mission03 с новым исполнителем не смешан: его отдельный проверенный сценарий, тесты и отчёты остаются. Mission02 — прежний приближённый планировщик FIFO/EDF/Priority для сравнения, но он ещё **не** отправляет решения в универсальный исполнитель. Автоматизация такой связи и новые оптимизационные методы относятся к следующему исследовательскому этапу.
