# Новый маршрут: от одного видимого спутника к исследованию группировки

**Согласованное направление:** сначала наблюдаем работающую орбитальную модель; затем постепенно добавляем аппаратуру, память, связь и задачи; после исследований одного КА переходим к группировке, затем к облачности.

## Веха 1 — спутник на орбите (первая задача)
**Результат:** вычисленная орбитальная траектория КА вокруг Земли; 3D-визуализация в Vizard (либо независимый открытый 3D-просмотрщик, если Vizard не удастся запустить); сохранённые таблицы координат и параметров движения.

- Начать с официального примера Basilisk `scenarioBasicOrbit`, не писать с нуля собственный пропагатор.
- На первом запуске — простая круговая расчётная орбита, **явно заданная как учебный сценарий**, а не траектория реально запущенного аппарата.
- Зафиксировать эпоху, высоту/большую полуось, наклонение, эксцентриситет, параметры Земли, модель гравитации, системы координат и шаг интегрирования.
- Проверить период аналитически для двухтельной модели, изменение сохраняемых интегралов, согласованность координат/единиц, сходимость по шагу.
- Записать версию Basilisk, Windows/Python, точную команду запуска и формат выходных файлов.
- Показать не только модель в 3D, но и графики высоты/координат/скорости и исходный JSON.
- **Не переносить исходники Basilisk в репозиторий**: устанавливать разрешённый программный пакет с зафиксированной версией.

**Готовность:** воспроизводимый запуск на Windows с Python 3.13, 3D-просмотр и отчёт по проверкам. Научная физическая достоверность конкретного КА этим ещё не доказана.

## Веха 2 — спутник с полезной нагрузкой
**Результат:** на основе вычисленной орбиты создаются окна допустимой съёмки и связи; КА формирует условные продукты, занимает память и передаёт данные на Землю.

- Сначала доступность одной наземной территории и станции.
- Далее модули целевой аппаратуры, памяти и радиосвязи — использовать подходящие готовые Basilisk-компоненты, но отдельно проверить их семантику, единицы и балансы.
- Подключить требования к заданиям/доставке из нашего текущего простого информационного симулятора через адаптер. *Не создавать две независимые «истины» для одного состояния памяти.*
- Для каждого численного параметра — паспорт/расчёт/синтетический, ссылка/редакция, единицы, границы допущения.

**Готовность:** один понятный полный цикл «окно → съёмка → продукт → память → окно связи → доставка» и его временная диаграмма; тесты сохранения данных.

## Веха 3 — исследования одного КА
**Результат:** сравнение методов планирования при фиксированной аппаратуре, орбите и заданиях.

- Базовый планировщик; вариант, учитывающий доставку; точный эталон небольших задач.
- Метрика — доля требований, для которых пригодные данные доставлены в срок, плюс причины отказов.
- Контрольные синтетические задачи, затем сценарии с подтверждёнными параметрами. Честно отделять верификацию кода от валидации модели.

## Веха 4 — группировка
**Результат:** N КА в одной модели, общие задания и наземные станции, изменяемое фазирование и орбитальные построения.

## Веха 5 — исследования группировки
**Результат:** сравнение планировщиков и конфигураций по единой программе наблюдений, расчёты K(N), объяснение ресурсоограниченных случаев.

## Веха 6 — облачность и дополнительные факторы
**Результат:** сценарный анализ влияния пригодности снимков на планирование, число КА и сроки доставки.

## Правила для ВСЕХ вех
1. Писать небольшие автоматические тесты **на каждой вехе**, не после всех исследований.
2. Новые модели подключать через документированные адаптеры с версиями и источниками; не переписывать сложную физику без причины.
3. Не подменять результат физической симуляции красивой анимацией.
4. Каждый PR: цель, происхождение входных данных, результаты проверок, ограничения, инструкции просмотра.
5. `main` остаётся работоспособной. Эксперименты и установка библиотек не должны перезаписывать v0.1.1.
