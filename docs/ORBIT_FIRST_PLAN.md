# Дорожная карта НИРС

Подробный текущий статус: [PROJECT_STATUS.md](PROJECT_STATUS.md). Этот план разделяет завершённые вехи, ближайший исследовательский этап и долгосрочные направления.

## Завершено: орбита, подсистемы и физический исполнитель

- Орбитальная динамика Basilisk, вращающаяся Земля и геометрическая видимость.
- Наведение реакционными колёсами, полезная нагрузка, память, энергия и условная передача.
- Физический исполнитель фиксированного порядка для точечных и полосных заданий.
- Mission 05: план/факт, WGS84-оценка покрытия, UTC/приближённый GMST.
- Локальная Windows-приёмка Mission 05: 16/16 на контрольном коммите `c65daa80c6612a876575337b39f9150223a3c531` по приложенным отчётам пользователя.

Эти результаты подтверждают программную модель на синтетических параметрах; они не калибруют реальный аппарат.

## Следующая веха: планирование для одного КА

Для Mission Control 02 требуется сравнить алгоритмы планирования нескольких заявок на одном аппарате, используя уже проверенный физический исполнитель. Планировщик должен составлять порядок операций, учитывать ограничения ADCS, энергии, памяти и связи, а модель — регистрировать отказ и подтверждённую в рамках модели условную доставку.

Критерии и текущая постановка: [GitHub issue #20](https://github.com/MrKorshunov/nirs-satellite/issues/20).

## Дальнейшие направления

1. Подбор и документирование паспортных характеристик конкретного класса КА, если исследовательская постановка их требует.
2. Оценка влияния шага, параметров и модельных упрощений на выводы.
3. После экспериментов одного КА — постановка для группировки и общих наземных ресурсов.
4. Дополнительные факторы, например облачность, только после определения измеримых KPI.

## Правила воспроизводимости

1. Не менять контрольные физические параметры при сравнении планировщиков без отдельного обоснования.
2. Отделять синтетические, паспортные и расчётные величины и указывать единицы/источник.
3. Проверять алгоритм отдельно от физического исполнителя и сверять малые случаи с точным эталоном.
4. Не считать статус GitHub Actions успешным, пока workflow не завершился с `success`.
5. Сохранять входы, версии зависимостей, команду запуска и ограничения каждого результата.
