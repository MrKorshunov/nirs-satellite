# Mission 02 — воспроизводимые эксперименты над одним КА

**Статус:** исследовательская модель выполнения программы ДЗЗ на основе
физически рассчитанной **Basilisk** траектории. Операционная модель
ресурсов является **собственной дискретной аппроксимацией**, а НЕ
собранной моделью всех физических приборов Basilisk. Числа синтетические.

## Главное отличие от Mission 01

Mission 01 сохраняется как проверенный интеграционный эталон:
`spacecraft → locationPointing → simpleInstrument → partitionedStorageUnit
→ spaceToGroundTransmitter`. Там один условный продукт.

Mission 02 формирует **несколько разных заданий** и конкурирующие операции.
На вход берёт действительные записанные позиции КА, рассчитанные
Basilisk в прежней `Ground 01`. Полёт заново не переписывается.
Геометрия остальных целей и станций рассчитывается по тем же
синтетическим координатам и вращению сферической Земли. Выполнение
планов реализовано отдельным детерминированным планировщиком.

Это **двухуровневая исследовательская архитектура**, а не обещание
высокой физической точности всех подсистем.

## Что ограничивается

| Ограничение | Как учитывается | Степень физической достоверности |
|---|---|---|
| Орбитальная динамика | Траектория от Basilisk `spacecraft` | Двухтельная, синтетическая, ранее верифицирована |
| Видимость | Угол места и вращение сферы | Геометрическая аппроксимация, произвольная эпоха |
| Камера | Угол отклонения от надира; экспозиция | Нет оптики/пикселей/солнце-угла |
| Наведение | Кинематический предел манёвра по моменту, инерции, скорости и импульсу RW; время успокоения | **Не** динамика `reactionWheelStateEffector` |
| Память | Ёмкость, последовательная очередь, освобождение по мере передачи | Идеальная память в битах |
| Энергетика | Батарея Wh, резерв, базовое/рабочее потребление, солнечная генерация в освещении | Упрощение; не `simpleBattery`, нет ориентации панелей |
| Затмение | Цилиндрическая тень Земли, постоянный вектор Солнца | Упрощение; не `eclipse` |
| Радиоканал | Угол места станции, дальность, Friis/EbN0, номинальный потолок скорости, только целые пакеты | Нет BER, антенны, кодирования/погоды и подтверждения приёма |
| Задачи | Время начала, срок сдачи, приоритет, размер продукта, окна, конфликт операций | Наша постановка |
| Политики | FIFO / EDF / Priority | Наши детерминированные базовые методы |

Использование названия «спутниковая физическая модель» **не означает**
соответствие реальному летавшему аппарату или полную валидацию подсистем.
Все численные паспортные параметры здесь **предположены**, а не
переписаны с паспорта конкретного производителя.

## Как запустить (Windows)

Из **корня репозитория**, где создана `.venv` с Python 3.13 и
`bsk[all,examples]==2.12.2`:

```powershell
.\\.venv\\Scripts\\python.exe -m unittest tests.test_mission02_model -v
.\\.venv\\Scripts\\python.exe -m experiments.mission_02.run --plan-only
.\\.venv\\Scripts\\python.exe -m experiments.mission_02.run --duration-hours 4 --step-s 10 --output-name mission02_trial_01
```

Можно запустить `RUN_MISSION02.cmd` двойным щелчком.
Файл `RUN_MISSION02_TESTS.cmd` проверяет математическую логику без Basilisk.

Для небольшого быстрого теста:

```powershell
.\\.venv\\Scripts\\python.exe -m experiments.mission_02.run --duration-hours 0.2 --step-s 10 --output-name mission02_smoke
```

Для серии экспериментов с одинаковой траекторией сначала создайте её
один раз (или воспользуйтесь сгенерированной при первом запуске):

```powershell
.\\.venv\\Scripts\\python.exe -m experiments.mission_02.run --track results\\mission02_trial_01_basilisk_geometry\\access.csv --duration-hours 4 --step-s 10 --radio-bps 20000 --output-name mission02_slow_radio
```

Входной `--track` **должен** быть файлом `access.csv` из Basilisk
Ground 01 (или с идентичным проверяемым форматом). Обязательное
условие — одинаковые единицы, эпоха и шаг. Изменённые конфигурации
сохраняются как `configuration_used.json` в папке результатов.

Для повторного запуска под тем же именем требуется явный `--overwrite`
(внимание: файлы отчёта под тем же именем будут заменены).
Для научных сравнений лучше использовать новые имена запусков.

## Результаты

В `results/<output-name>/`:
- `manifest.json` — SHA-256 входного файла и траектории, версия/ограничения;
- `configuration_used.json` — фактическая исходная конфигурация;
- `comparison.csv`, `comparison.json` — результаты политик;
- `fifo_states.csv`, `edf_states.csv`, `priority_states.csv` — временные ряды;
- `*_events.json` — журнал команд, съёмок и передачи.
- `*_summary.json` — KPI, энергетика, память, допущения.

**Основной KPI:** сумма весов заданий, чьи данные условно переданы
полностью до указанного срока, делённая на сумму весов всех заданий.
`delivered_on_time` не означает независимое подтверждение радиоприёма.

Снимок данных не является фото: это объём бит с тегом задания.

## Что ещё нужно для физически подробной модели

1. Адаптировать Basilisk `scenarioAttitudeFeedbackRW` с
`reactionWheelStateEffector`, `rwMotorTorque`, реальными ограничениями,
получить проверенные времена перенаведения. Сверять с приближением Mission 02.
2. Адаптировать `scenarioPowerDemo` (& солнце/затмение/ориентация) и
использовать вычисленные энергетические профили вместо постоянной мощности.
3. Реализовать физически контролируемую многозадачную съёмку с
`simpleInstrumentController` и приоритетной передачей по нескольким
`partitionedStorageUnit` разделам. Проверить на Basilisk именно
исполнение оптимизированного расписания.
4. При выборе настоящего класса КА заменить синтетические параметры
с паспортами, указать погрешности и проверить физическую реализуемость.
5. Сравнить планировщики с OR-Tools CP-SAT (эталон оптимальности для
малых задач), провести анализ по шагу, массе данных, скорости и энергетике.

**Важное правило:** результаты Mission 02 нельзя объявлять
результатами динамической симуляции работы маховиков/электропитания/
радиоаппаратуры. Сценарий предназначен для первых исследований
алгоритмов с явно ограниченной достоверностью подсистем.
