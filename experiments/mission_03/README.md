# Mission 03 — единый физический исполнитель спутника

**Главный режим НИРС**: один непрерывный расчёт Basilisk 2.12.2,
в котором КА наводится последовательно на две разные наземные цели,
создаёт два условных продукта данных, сохраняет их и передаёт
на станцию при геометрической доступности.

## Что вычисляется физическими модулями Basilisk

1. Орбита и динамика корпуса: `spacecraft`, гравитация Земли.
2. Вращение Земли, геометрия: `planetEphemeris`, `groundLocation`.
3. Наведение: `simpleNav`, `locationPointing`, `mrpFeedback`.
4. Исполнительные органы: `rwMotorTorque`, `reactionWheelStateEffector`,
   три ограниченных синтетических реакционных колеса.
5. Камера: `simpleInstrumentController`, `simpleInstrument` — один объёмный
   цифровой продукт на цель, не настоящая оптическая фотография.
6. Память и передача: `partitionedStorageUnit`, `spaceToGroundTransmitter`.
   Два раздела памяти; битовый баланс и проверка доступности станции.
7. Электроэнергия: `eclipse`, `simpleSolarPanel`, `simplePowerSink`,
   `simpleBattery`. Телеметрия реального заряда служит основанием
   для команд разрешения и запрета операций.

## Физическое переключение между целями

Специальный `PhysicalMissionDirector` — модуль Python, наследующий
`Basilisk.architecture.sysModel.SysModel`. Он работает **внутри**
динамической задачи Basilisk, после расчёта текущей геометрии, камеры,
памяти и батареи.

После первого продукта:
- принимает подтверждение генерации по физическому сообщению прибора;
- вызывает `groundLocation.specifyLocation()` для второй цели;
- назначает второй раздел данных `simpleInstrument.nodeDataName`;
- устанавливает `simpleInstrumentController.imaged=0`;
- не перезапускает КА, маховики, аккумулятор, память и радио.

Вторая съёмка разрешена только после реального нового наведения.
Это тот же проверенный принцип смены цели, что в официальном
`scenarioGroundLocationImaging`, но с реальной динамикой RW и энергетики.

## Связь с энергосистемой

С периодом `control_step_s` директор читает **вычисленный Basilisk**
заряд аккумулятора, применяет порог `reserve_wh` + `reserve_guard_wh`
и гистерезис восстановления. При низком заряде команды камеры и радио
блокируются, а соответствующие `SimplePowerSink.powerStatus`
переключаются. Базовая нагрузка шины продолжает действовать.

Проверка резерва дискретная, поэтому абсолютно точное поддержание
порога в экстремальных режимах не гарантировано. Превышение ограничений
фиксируется, а не скрывается.

## Исходные данные

Запуск на Windows: `START_NIRS.cmd` → «Все исходные данные».
Редактор создаёт резервные копии при сохранении.

| Файл | Содержание |
| --- | --- |
| `inputs/physical/mission_execution.json` | Две разные цели, порядок, срок, интервал управления, энергетический резерв |
| `inputs/physical/orbit.json` | Орбита, масса и моменты инерции |
| `inputs/physical/earth_target.json` | Вращение синтетической Земли |
| `inputs/physical/adcs_wheels.json` | Динамика маховиков и регулятор |
| `inputs/physical/power.json` | Батарея, панель, нагрузки |
| `inputs/physical/camera_storage_radio.json` | Объём продукта, память, битрейт, станция |

Эти файлы используются напрямую, без новой дублирующей таблицы
характеристик аппарата.

## Запуск

**Обычный:** двойной щелчок по `START_NIRS.cmd` → физический сценарий
с двумя целями → «Запустить».

**Контрольный:** двойной щелчок по `CHECK_NIRS.cmd`.

**Для разработчика** (из корня проекта):

~~~powershell
.\.venv\Scripts\python.exe -m experiments.mission_03.run --duration-hours 0.2 --viz-mode file --viz-step-s 10 --require-two-captures --output-name mission03_manual
~~~

Результаты в `results/ИМЯ_ЗАПУСКА/`:
- `mission03_summary.json` — проверки, времена и число съёмок
- `mission03_events.json` — хронология смены целей и энергорежимов
- `mission03_states.csv` — кадры данных, заряд, память, RPM, наведение
- `mission03_dataflow.png` — графики
- `power_summary.json` и `power_states.csv` — энергетика
- запись Vizard `.bin` — в локальной папке Vizard

## Что демонстрация НЕ моделирует

- Реальную эпоху UTC, J2, атмосферное сопротивление и WGS84.
- Шумы навигационных датчиков, магнитную разгрузку и настоящие
  паспортные характеристики колёс.
- Реальную фотоматрицу, оптику, обработку/сжатие изображения.
- Реальный наземный приёмник, ошибки радиопакетов и подтверждение ACK.
- Термические, механические, радиационные и отказные процессы.
- Выбор лучшего расписания и его оптимизацию.

**Важная граница:** пока это физический исполнитель двух тестовых
заданий. Наши оптимизационные алгоритмы появятся позже, как отдельный
исследовательский слой, когда этот исполнитель пройдёт приёмку на Windows.
